# Тестирование и проверки

Единственный способ принять изменение — успешный `make verify` (шаги и их
назначение — в [README](../README.md#make-verify) и [CONTRIBUTING](../CONTRIBUTING.md)).
Здесь — как устроены тесты, как изолированы данные и какие функции ТЗ
покрыты.

## Запуск

```bash
make test        # все тесты + покрытие + отчёты (нужен PostgreSQL)
make test-unit   # только unit-тесты, без базы данных, ~1 с
make mutation    # мутационная проверка app/rules.py
make verify      # всё обязательное по порядку
```

Для отладки можно запустить один тест —
`.venv/bin/python -m pytest tests/unit/test_rules.py::test_bp04_valid_date -v`, —
но изменение принимается только по итогам полного `make verify`.

## Состав

| Каталог | Что проверяется | База данных |
|---|---|---|
| `tests/unit/test_rules.py` | Правила БП-01 … БП-10: верные, ошибочные и граничные значения; ошибки и их коды | нет |
| `tests/unit/test_auth.py` | Сеанс в подписанном cookie: подпись, подделка, срок действия до секунды; настройки и их ошибки | нет |
| `tests/unit/test_helpers.py` | Разбор полей экранных форм; параметры подключения для резервного копирования | нет |
| `tests/integration/test_api.py` | Все методы HTTP API: правила на настоящей базе, права ролей, коды ответов, отказ базы, скрытие внутренних ошибок | да |
| `tests/integration/test_web.py` | Экранные формы: вход, справочники, поступления, отчёт, пользователи; сообщения об ошибках | да |
| `tests/integration/test_migrations.py` | Миграции: чистая база, база с данными, откат каждой миграции, совпадение схемы с моделями | временная |
| `tests/integration/test_dbadmin.py` | Резервная копия → намеренное повреждение → восстановление; отказ на испорченном файле | да |
| `tests/integration/test_seed.py` | Начальное и демонстрационное наполнение, повторный запуск без дублей, запуск приложения | да |

Unit-тесты проверяют основную логику — правила предметной области
(`app/rules.py`) — как чистые функции. Интеграционные тесты проходят весь путь
«HTTP-запрос → операция → PostgreSQL → ответ» и проверяют то, что живёт в
базе: ограничения, внешние ключи, вычисляемую сумму строки, транзакции.

## Тестовая конфигурация и изоляция данных

- **Отдельная база.** Тесты работают с базой из `TEST_DATABASE_URL` (по
  умолчанию — рабочая база с суффиксом `_test`). Приложение в тестах видит
  только её: `tests/conftest.py` подменяет `DATABASE_URL` до импорта кода.
- **Защита рабочих данных.** Имя тестовой базы обязано оканчиваться на
  `_test`, иначе прогон останавливается с сообщением: тесты очищают таблицы.
- **Свои параметры приложения.** `SECRET_KEY`, пароль администратора, срок
  сеанса и прочее задаются в `tests/conftest.py`, а не берутся из `.env`
  разработчика: результат не зависит от локальных настроек.
- **Схема из миграций.** В начале прогона тестовая база создаётся (если её
  нет) и приводится к последней версии командой `alembic upgrade head` — те
  же миграции, что на рабочей базе.
- **Чистые таблицы перед каждым тестом** (`TRUNCATE … RESTART IDENTITY`):
  тесты не зависят друг от друга и от порядка запуска; каждый создаёт свои
  данные сам.
- **Временные базы.** Тесты миграций создают отдельную базу
  `*_migrations_test` и удаляют её после себя.

## Ошибочные данные, граничные случаи, обязательные правила

| Правило | Граница — принимается | За границей — отказ |
|---|---|---|
| БП-02 количество | `0.001`; `1.234` (3 знака); `3.000` для штук | `0`, `-0.001`, `1.2345`, `1.5` для штук |
| БП-03 цена | `0`, `0.01`, `1.23` | `-0.01`, `1.234` |
| БП-03 сумма | `2.5 × 0.01 = 0.03` (половина — вверх) | — |
| БП-04 дата | `01.01.2000`, сегодня | `31.12.1999`, завтра |
| БП-05 ИНН | 10 и 12 цифр, контрольная цифра из остатка 10 | неверная 10-я, 11-я, 12-я цифра; 9, 11, 13 цифр; буквы; замена любой цифры |
| БП-06 артикул | 3 и 32 символа | 2 и 33 символа, кириллица, пробел, `_` |
| БП-10 пароль | ровно 8 символов (и ровно `PASSWORD_MIN_LENGTH`) | 7 символов, пусто |
| Логин | 3 и 50 символов, `.` `-` `_` | 2 и 51 символ, кириллица, пробел, `@` |
| Сеанс | ровно `SESSION_HOURS` часов | на секунду позже; чужая или изменённая подпись; испорченное содержимое |
| Отчёт, отбор | границы периода включены; `date_from = date_to` | `date_from > date_to` |
| Наименование, телефон, ФИО | 3 и 200, 5 и 20, 3 и 150 символов | на символ короче или длиннее |

Обязательные правила проверяются и на уровне API и форм: повтор материала в
поступлении (БП-07), удаление записи со ссылками (БП-08), операции
администратора для кладовщика (БП-09), неизвестные поля в JSON, отказ базы
данных (`/healthz` → 503), непредвиденная ошибка (500 без подробностей для
пользователя, подробности — в журнал).

## Мутационная проверка

`tools/mutation.py` по одному вносит в `app/rules.py` изменения логики —
`<` → `<=`, `==` → `!=`, `and` → `or`, удаление `not`, `10` → `11` и `10` → `9`,
`*` → `/`, `True` → `False` и т. д. — и для каждого запускает unit-тесты.
Изменение, которое тесты не заметили, «выживает» и выводится с номером строки.
Порог — 100 %: сейчас все 154 мутации обнаруживаются.

Так автоматически воспроизводится проверка на защите «преподаватель изменяет
одно условие в основной логике». Вручную:

```bash
# например, в validate_receipt_date заменить  value < MIN_DATE  на  value <= MIN_DATE
make test-unit
# FAILED tests/unit/test_rules.py::test_bp04_valid_date[value1] — 01.01.2000 отвергнута
```

Проверка других файлов (медленнее, с базой данных):
`.venv/bin/python tools/mutation.py --target app/services.py --tests tests --jobs 1`.

## Миграции

`tests/integration/test_migrations.py`:

- `test_migrations_form_one_chain` — миграции образуют одну цепочку без ветвлений;
- `test_clean_database` — чистая база → `upgrade head` → схема совпадает с
  моделями `app/models.py` (`alembic.autogenerate.compare_metadata`), у каждого
  ограничения базы есть понятное сообщение в `rules.DB_ERRORS`;
- `test_every_migration_can_be_reverted` — вверх по одной миграции, вниз до
  пустой базы, снова вверх;
- `test_upgrade_database_with_data` — база заполняется данными в схеме первой
  версии, затем обновляется до последней; данные и суммы строк сохраняются.

## Ошибки, найденные новыми тестами

При расширении набора тестов найдены и исправлены ошибки, которые прежние
35 тестов не замечали:

1. **Страница ошибки для вошедшего пользователя падала с 500.** Если операция
   отказывала (404, 403, 409) вне формы — например, `/receipts/9999` или
   `/users` для кладовщика, — транзакция откатывалась, объект пользователя
   становился недоступен, и шаблон страницы ошибки падал
   (`DetachedInstanceError`). Исправлено в `app/auth.py`: пользователь сеанса
   отвязывается от сеанса базы данных сразу после загрузки.
2. **Изменение единицы измерения материала через API** возвращало в ответе
   прежнюю единицу (обновлялся только внешний ключ, а не связь). Исправлено в
   `services.save_material`.
3. **Повреждённый хеш пароля с не-ASCII символами** вызывал 500 при входе
   вместо отказа. Исправлено в `auth.verify_password`.
4. **`make demo_seed` без администратора** оставлял открытой транзакцию.
   Добавлен `db.session_scope()`, начальное и демонстрационное наполнение
   переведены на него.
