# Непрерывное развертывание (ЛР6)

CD принимает релиз только после проверки в целевой среде: успешная сборка и
публикация образа — ещё не релиз. Workflow — `.github/workflows/cd.yml`,
окружение — ВМ **wa-stage01** (192.168.253.132), файлы — `deploy/stage/`.

```
 GitHub Actions                          wa-app01                  wa-stage01
 ──────────────                          ────────────────          ─────────────────
 CI (master) ──► publish ──► реестр      runner ◄── CD deploy      пользователь deploy
 127.0.0.1:5000 ───────────────────────────────► registry (LAN,    docker pull
        ▲                                        DOCKER-USER: только .132)    │
        └────────── deploy.sh <тег> по SSH ───────────────────────────┘
                       verify.sh <тег>: контейнеры → /healthz → /version → сценарий
```

## Пункты задания

| П. | Решение |
|---|---|
| 1. Отдельное окружение | wa-stage01: своя ВМ, свой compose-проект `warehouse-stage`, своя БД в контейнере |
| 2. Отдельная учётная запись | пользователь `deploy`: вход по ключу, без sudo, группа `docker`; ключ — секрет `STAGING_SSH_KEY` окружения `staging` |
| 3. Образ из реестра | в `deploy/stage/compose.yaml` нет секции `build`; `deploy.sh` делает только `docker compose pull`. Реестр открыт в подсеть стенда (iptables DOCKER-USER: порт 5000 только с wa-stage01), аутентификация htpasswd сохранена |
| 4. Настройки отдельно от образа | `/srv/warehouse-stage/env/*.env` на сервере (root:deploy, 640); в репозитории — только `*.example`; версия сборки приходит в образ при сборке (ENV APP_VERSION/APP_REVISION) |
| 5. Автоматическое развертывание | триггер `workflow_run` по успешному CI в `master`; тег вычисляется из коммита, который проверял CI |
| 6. Ограничение развертывания | автоматическое — только `master`; ручное — только с явным тегом; окружение `staging` с политикой веток `master` |
| 7. Проверка релиза | `deploy/stage/verify.sh`: контейнеры healthy и миграции завершены → `/healthz` → `/version` == развёрнутый тег → сценарий: вход → поставщик → материал → поступление со строкой → отчёт по поставкам (созданные записи удаляются) |
| 8. Адрес версии | `GET /version` — версия и полный хеш коммита сборки из ENV образа; проверяется тестами |
| 9. Неуспешная проверка | падение `verify.sh` = красное задание = релиз не принят |
| 10. Тег и возврат | `workflow_dispatch` с параметром `tag`; возврат предыдущей версии — тот же запуск с прежним тегом из `registry_tags.sh` |
| 11. Конфликты развертываний | `concurrency: cd-staging` без отмены: развертывания в очередь, не наполовину |
| 12. Сквозной выпуск | фича `/version`: задача → ветка → `make verify` → запрос на слияние → CI → образ → авто-развертывание → зелёная проверка |
| 13. Неудачный выпуск | заведомо сломанный образ отдельным тегом → развертывание → красная проверка → ручной возврат прежнего тега |

## Секреты (окружение `staging`, только ветка master)

| Секрет | Для чего |
|---|---|
| `STAGING_SSH_KEY` | закрытый ключ учётной записи `deploy` на wa-stage01 |
| `REGISTRY_USER`, `REGISTRY_PASSWORD` | проверка наличия образа в реестре до развертывания |

Ключ хоста wa-stage01 закреплён в `deploy/stage/known_hosts`
(`StrictHostKeyChecking=yes`) — подмена сервера невозможна.

## Неудачи (проверка на защите)

| Сценарий | Что происходит |
|---|---|
| Неверный тег | образ не найден в реестре — задание падает до развертывания |
| Отсутствующая переменная | приложение не запускается без обязательной переменной — контейнер не healthy, проверка красная |
| Неуспешный healthcheck | контейнер app не становится healthy — проверка красная |
| Приложение стартует, но сценарий не работает | шаг 4 `verify.sh` красный — именно поэтому проверка не ограничивается healthcheck |
| Недоступный registry | шаг «Образ есть в реестре» красный; текущая версия на окружении не меняется |
| Возврат предыдущей версии | ручной запуск CD с прежним тегом → зелёная проверка |
