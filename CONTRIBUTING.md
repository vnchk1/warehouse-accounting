# Правила внесения изменений

Документ обязателен для всех участников команды. Любое изменение — код,
схема данных, зависимости, настройки проверок — проходит один и тот же
проверочный контур дважды: локально (`make verify`) и на сервере CI
(GitHub Actions, [docs/CI.md](docs/CI.md)) — те же команды с теми же версиями.
CI — независимый обязательный барьер: образ приложения собирается и
публикуется только после успеха всех его проверок.

## Порядок работы

```
задача → ветка → несколько осмысленных коммитов → make verify →
git push (хук снова запускает make verify) → CI по отправке →
запрос на слияние → CI по запросу → одобрение участника (и владельцев
критических файлов — CODEOWNERS) → слияние в master → CI по master →
публикация образа <версия>-<коммит> в реестр → тег версии
```

1. **Задача.** Любое изменение начинается с задачи, в которой описано, что
   должно получиться и как это проверить.
2. **Ветка** от актуальной основной ветки:
   `feature/<номер задачи>-<краткое-описание>` — новая функция,
   `fix/<номер задачи>-<краткое-описание>` — исправление,
   `docs/<номер задачи>-<краткое-описание>` — документация.
3. **Коммиты.** Несколько осмысленных коммитов с номером задачи:
   ```
   feat(receipts): добавление строк поступления (#4)
   fix(suppliers): контрольная сумма ИНН из 12 цифр (#7)
   test(rules): проверка БП-02 для штучных единиц (#4)
   ```
4. **Проверки.** До создания запроса на слияние обязателен успешный
   `make verify`. Хук `pre-push` (включается `make setup` или `make hooks`)
   запускает его перед каждым `git push` и отменяет отправку при ошибке.
5. **Запрос на слияние** содержит ссылку на задачу, описание изменения,
   способ проверки и итог `make verify` (последние строки вывода). Слить его
   можно только при успехе всех обязательных проверок CI (правило защиты
   ветки master): красный CI не обходится, а исправляется новым коммитом.
6. **Проверка изменений.** Не менее одного другого участника команды смотрит
   код: соответствует ли задаче, есть ли тесты, не ослаблены ли проверки.
   Автор обязан объяснить любую строку своего изменения.
7. **Слияние** после устранения замечаний, ветка удаляется.
8. **Тег версии** на состояние основной ветки: `git tag -a v0.1.0 -m "…"`.

## Обязательный набор проверок — make verify и CI

| Шаг | Команда | Задание CI | Что проверяет |
|---|---|---|---|
| 1 | `make policy` | Стиль и правила проекта | Правила этого документа, которые можно проверить автоматически (`tools/policy.py`) |
| 2 | `make guard` | Охрана приёмки | Pipeline не ослаблен, CODEOWNERS полон, тесты не удалены, правила не ослаблены (`tools/ci_guard.py`) |
| 3 | `make format-check` | Стиль и правила проекта | Форматирование (`ruff format --check`); исправить — `make lint` |
| 4 | `make lint-check` | Стиль и правила проекта | Линтер (`ruff check`) |
| 5 | `make sast` | Безопасность | Анализ безопасности кода (`bandit`) |
| 6 | `make secrets` | Безопасность | Секреты в файлах и коммитах ветки (`gitleaks`) |
| 7 | `make deps-audit` | Безопасность | Известные уязвимости зависимостей (`pip-audit`) |
| 8 | `make test` | Тесты | Unit- и интеграционные тесты; покрытие кода не ниже порога |
| 9 | `make mutation` | Тесты | Тесты обнаруживают изменение любого условия в правилах `app/rules.py` |
| 10 | `make migrations-check` | Миграции | Миграции на отдельной временной базе: применение, откат, повторное применение |
| 11 | `make backup-check` | Резервное копирование | Копия → повреждение → восстановление на временной базе |

Изменение принимается, только если все шаги прошли и локально, и в CI.
Контейнерные шаги (`make container-check`: правила, сборка, проверка образа,
анализ уязвимостей trivy) выполняют задания CI «Контейнерная проверка»,
«Сборка образа» и «Анализ образа», а на сервере — `make container-up`.
Отчёты — в каталоге `reports/` (в репозиторий не попадает) и в артефактах
прогона CI.

## Запрещено

**Пропускать тесты.** Нельзя удалять или отключать тесты, в том числе
«временно»: отметки `skip`, `skipif`, `xfail`, вызовы `pytest.skip()`,
`pytest.xfail()`, `pytest.importorskip()`, отбор тестов ключами `-k`,
`--deselect`, `--ignore`. Нарушение ловится дважды: `make policy` находит
такие места в коде, а сам прогон тестов превращает любой пропуск в ошибку
(`tests/conftest.py`). Тест, который мешает, исправляют или исправляют код.

**Снижать пороги.** Нельзя уменьшать порог покрытия (`fail_under` в
`pyproject.toml`), порог мутационной проверки (`min_score`) и сужать её
охват (`target`). Нижние границы записаны в `tools/policy.py`
(`COVERAGE_FLOOR`, `MUTATION_FLOOR`, `MUTATION_TARGET`). Порог можно только
повышать. Изменение нижней границы — отдельная задача с обоснованием в
запросе на слияние и проверкой двумя участниками.

**Добавлять исключения анализаторов без обоснования.** Исключение допустимо
только точечное и с причиной рядом с ним:

| Где | Как правильно |
|---|---|
| строка кода, ruff | `# noqa: T201 — причина` (конкретное правило, затем пояснение) |
| строка кода, bandit | строкой выше `# Безопасно: причина`, в строке `# nosec B603`; либо `# nosec B404  # причина` |
| строка, gitleaks (ложное срабатывание поиска секретов) | `# gitleaks:allow — причина`; общие исключения в `.gitleaks.toml` запрещены (`make guard`) |
| образ, trivy | строка в `.trivyignore`: `CVE-… # причина; пересмотреть до …` — только с меткой `acceptance-change` |
| `pyproject.toml` | каждое значение в `ignore`, `per-file-ignores`, `skips`, `exclude_dirs`, `exclude_also`, `omit`, `filterwarnings` — с комментарием над ним или в той же строке |

Общие отключения (`# noqa` без кода, `# nosec` без кода, правило в `skips`
«на всякий случай») запрещены. Всё это проверяет `make policy`.

**Также запрещено:**

- менять версии зависимостей не точным значением (только `==`) и в обход
  задачи; после изменения версий — `make install` и `make verify`;
- убирать шаги из `make verify` и добавлять в его команды ключи, ослабляющие
  проверки (`--exit-zero`, `--cov-fail-under` и т. п.);
- отправлять изменения в обход хука (`git push --no-verify`);
- писать напрямую в основную ветку и перезаписывать её историю (`git push --force`);
- добавлять в репозиторий файл `.env`, пароли, ключи, резервные копии и
  файлы среды разработки;
- менять схему базы данных в обход миграций; миграцию нельзя менять после
  того, как она попала в основную ветку — только новой миграцией;
- сливать изменения без проверки другим участником;
- отключать или ослаблять проверки CI: удалять задания и шаги из
  `.github/workflows/ci.yml`, добавлять `continue-on-error`, `|| true`,
  `if: always()` (кроме сохранения отчётов), публиковать образ в обход
  зависимости от всех проверок; всё это находит `make guard`;
- менять критические файлы приёмки (тесты, `Makefile`, `pyproject.toml`,
  `tools/`, `.github/`, `migrations/`, настройки анализаторов, контейнерные
  файлы — полный список в `.github/CODEOWNERS`) без одобрения их владельцев;
- держать пароли и токены где-либо, кроме секретов GitHub (`CI_DB_PASSWORD`,
  `REGISTRY_USER`, `REGISTRY_PASSWORD`) и файлов `.env` вне репозитория;
- добавлять исключения поиска секретов иначе, чем строкой
  `# gitleaks:allow — причина`, и исключения уязвимостей в `.trivyignore` без
  причины и срока пересмотра.

**Согласованное ослабление.** Иногда удалить тест или изменить порог
действительно нужно (тест заменён более точным, правило устарело). Тогда
`make guard` в CI останавливает запрос на слияние, пока на него не поставлена
метка `acceptance-change`; в описании запроса — причина. Метка не отменяет
одобрение владельцев критических файлов: ослабление всегда видно и всегда
проверено вторым участником. Локально то же — `GUARD_APPROVED=1 make verify`.

## Контейнерное окружение

Dockerfile, `.dockerignore`, `compose.yaml`, `requirements.lock` и `deploy/docker/`
меняются так же, как код: задача, ветка, `make verify`. Дополнительно:

1. Перед любым изменением работающего окружения — **`make container-check`**.
   Окружение изменяется только командой `make container-up`, которая сама начинает
   с `make container-check` и не выполняется при его ошибке. Запускать
   `docker compose up` в обход проверки запрещено.
2. После изменения версий в `pyproject.toml` или базового образа — `make lock`,
   новый `requirements.lock` сохраняется в проекте вместе с этим изменением.

**Запрещено** (проверяет `make container-check`, `tools/container_policy.py`):

- образы с тегом `latest` или без точной версии и дайджеста `@sha256:`;
- запуск процессов контейнеров от root (`USER root`, `user: "0"`, отсутствие `user`
  у готовых образов), `privileged`, `cap_add`, `network_mode: host`;
- секреты в образе: `ENV`/`ARG` с паролями, `COPY` файлов `.env`, пароли в
  `compose.yaml`; пароли хранятся только в `deploy/docker/env/*.env` (600, вне git);
- отключение healthcheck (`disable: true`, `HEALTHCHECK NONE`) и сервисы без него;
- публикация портов, кроме порта Nginx: порты приложения и базы наружу не открываются;
- сервисы без ограничений ресурсов (`cpus`, `memory`, `pids`).

## Изменение схемы базы данных

1. Новая миграция в `migrations/versions/` с номером, следующим за последним
   (`0005_…`), и обязательной функцией `downgrade()`.
2. Модели в `app/models.py` описывают ту же схему: тест
   `test_clean_database` сравнивает их со схемой после миграций.
3. Если миграция работает с уже существующими данными, она дополняет тест
   `test_upgrade_database_with_data` (база, заполненная в старой версии схемы).
4. Каждое новое ограничение базы получает понятное сообщение в
   `rules.DB_ERRORS` — это тоже проверяет `test_clean_database`.

## Разрешение конфликта слияния

```bash
git switch feature/4-receipt-items
git fetch origin
git merge origin/master
# разрешить конфликт, убрать маркеры <<<<<<< ======= >>>>>>>
make verify
git add <файлы>
git commit          # отдельный коммит с разрешением конфликта
git push
```

## Порядок приёмки

Изменение считается принятым, если:

1. `make verify` выполняется без ошибок, и все обязательные проверки CI
   по запросу на слияние успешны;
2. изменение соответствует задаче и сопровождается тестом;
3. другой участник команды подтвердил изменение в запросе на слияние, а при
   изменении критических файлов — их владелец из `.github/CODEOWNERS`;
4. в репозитории нет секретов и локальных файлов (`git ls-files | grep .env`
   не находит ничего, кроме `.env.example`);
5. приложение запускается по инструкции из README на чистой машине
   (`make setup && make run`).

## Зоны ответственности

| Участник | Зона |
|---|---|
| Участник 1 | Материалы и единицы измерения |
| Участник 2 | Поставщики |
| Участник 3 | Поступления и отчёт |
| Совместно | `app/config.py`, `app/db.py`, `app/auth.py`, `migrations/`, `Makefile`, `tools/`, `pyproject.toml`, `.github/`, документация |

Изменения общих файлов и миграций выделяются в отдельную задачу и
рассматриваются не менее чем двумя участниками.
